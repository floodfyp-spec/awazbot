## 1. Product in one paragraph

AwazBot KP is a website + voice platform for Khyber Pakhtunkhwa (Pakistan). Small service providers (electricians, UPS/solar technicians, AC/fridge mechanics, plumbers) each get their own AI voice receptionist that speaks **Pashto and Urdu**. Customers find providers on the website and **talk to the agent by voice** (real-time web call, or WhatsApp voice notes) to describe a problem and book a visit. A platform-level **"Find a service" (directory) agent** matches a spoken request ("I need an electrician in Hayatabad tomorrow") to providers and hands the caller to that provider's agent in the same call. Built for the KPITB AI Innovation Challenge 2026 (finale 13–15 Nov 2026); judges score real AI (not a wrapper), a live working prototype, KP impact, Pashto/Urdu UX, safety/privacy, and affordability.

- P0 Call log with transcript, language, outcome, duration, safety flag.

## 5. Agent behaviour

### 5.1 Platform rules (fixed template, providers cannot change)
1. First sentence discloses it is an automated assistant for <business>.
2. Speak in the caller's language (ps/ur; en if caller uses English). Short sentences, max 2 per turn.
3. Collect **one missing detail at a time**: problem → name → area + landmark → preferred time.
4. Before booking, **read back** name, problem, area, time and ask for confirmation.
5. Quote prices only within the provider's configured ranges; otherwise say the provider will confirm.
6. Never give repair or electrical/gas instructions beyond the fixed safety message.
7. If unsure or asked something outside the config, offer a callback from the provider.
8. Never invent availability; always use `check_availability`.

### 5.2 Provider agent tools (function tools)
| Tool | Behaviour |
|---|---|
| `classify_issue(text)` | Returns `{trade, issue_code, urgency}` using hybrid: ontology synonym match + LLM choice constrained to valid codes; if they disagree take the **higher** urgency |
| `update_booking_draft(name?, area?, problem_text?, preferred_time?, confirmed?)` | Writes to session state; publishes draft JSON to the room on data topic `awaz.booking` |
| `check_availability(urgency, day)` | Returns free slots from `working_hours` minus existing bookings and `max_jobs_per_day` |
| `create_booking()` | **Guard in code:** refuses unless name, area, issue, slot and `confirmed=true` are present; returns which fields are missing. On success inserts `bookings` (status `pending` or `confirmed` if auto-confirm) and triggers provider notifications: **email (always)** + WhatsApp alert (if enabled). A failed email must never fail the booking; it is logged in `notifications` and retried once |
| `answer_faq(question)` | Returns best matching FAQ answer from config or `null` |
| `escalate_to_provider(reason)` | Flags call for human callback + notifies provider |

### 5.3 Directory agent tools
| Tool | Behaviour |
|---|---|
| `search_providers(trade?, area?, language?, day?)` | Approved providers only; rank: serves area > open on day > rating; return top 3 with name, price range, areas |
| `describe_provider(provider_id)` | Short spoken summary |
| `connect_to_provider(provider_id)` | Loads that provider's config and **hands off** to a `ProviderAgent` in the same session (LiveKit Agents agent handoff); update call row `mode=provider, provider_id` |

### 5.4 Safety guard (runs before the LLM)
- On every **final** user transcript, normalise text (unify ی/ي, ک/ك, strip diacritics, lowercase Latin) and match `safety_rules` keywords (per language incl. Roman Urdu).
- On match: interrupt current speech, play the pre-rendered safety clip in the caller's language (fallback: TTS of the safety text), insert `safety_events`, set call `outcome=emergency`, publish `{"emergency": true}` on data topic `awaz.events`, notify provider (**emergency email** + WhatsApp if enabled), then continue collecting the address.
- Rules seeded for: gas smell/leak, sparks/burning smell/shock, flooding/burst pipe, injury. Tune for recall.

### 5.5 Agent config JSON (stored in `agent_configs.config`)
```json
{
  "agent_name": "Khan Electric assistant",
  "greeting": {"ps": "…", "ur": "…"},
  "languages": ["ps", "ur"],
  "voices": {"ps": "ps-AF-GulNawazNeural", "ur": "ur-PK-AsadNeural"},
  "tone": "respectful, short sentences",
  "trades": ["electrician", "ups_solar"],
  "services": [{"name": "UPS repair", "price_from": 1500, "price_to": 4000}],
  "areas": ["Hayatabad", "University Town"],
  "emergency_available": true,
  "booking": {"auto_confirm": false, "min_notice_hours": 2, "max_jobs_per_day": 6},
  "faq": [{"q": "Visit charge?", "a": "500 rupees, waived if repaired."}],
  "escalation_whatsapp": "+92XXXXXXXXXX"
}
```
`core/awaz_core/instructions.py::compile_instructions(config, mode)` = platform template (§5.1) + provider facts. Unit-tested.

### 5.6 Language handling
Start in the config's first language (directory agent: Urdu greeting with "Pashto or Urdu?" option). Detect caller language from the first final transcript; switch STT language and TTS voice for subsequent turns. Store per-turn `lang`.

## 6. Data model (Supabase)

Tables (all with `id uuid default gen_random_uuid()` unless noted, `created_at timestamptz default now()`):

- `providers(owner_user_id → auth.users, business_name, slug unique, provider_code unique (e.g. KHAN-01), status check in (pending,approved,suspended), whatsapp, notify_email text not null (check: valid email format), email_notifications bool default true, languages text[], trades text[], rating numeric default 0, about)`
- `notifications(booking_id null, call_id null, provider_id, channel check in (email,whatsapp), kind check in (new_booking,emergency,test,status_change), recipient, status check in (sent,failed), error text, ts)` — every email/WhatsApp alert attempt (never store message bodies with full phone numbers)
- `provider_services(provider_id, name, price_from int, price_to int)`
- `provider_areas(provider_id, area)`
- `working_hours(provider_id, weekday int 0-6, opens time, closes time)`
- `agent_configs(provider_id, version int, config jsonb, is_active bool)` — unique active per provider
- `customers(phone text unique null, wa_id text unique null, name, preferred_lang)`
- `calls(channel check in (web,wa_voice_note,wa_call), mode check in (directory,provider), provider_id null, customer_id null, room_name, started_at, ended_at, duration_s, language, outcome check in (booked,info,emergency,dropped,test), is_test bool default false, avg_latency_ms int)`
- `call_turns(call_id, speaker check in (customer,agent,system), text, lang, stt_engine, confidence real, latency_ms int, ts timestamptz)`
- `bookings(provider_id, customer_id, call_id, issue_code, urgency, problem_text, area, slot_start timestamptz, status check in (pending,confirmed,rejected,done), customer_name, customer_phone)`
- `safety_rules(code unique, keywords jsonb, message jsonb, active bool)`
- `safety_events(call_id, rule_code, matched_text, actions text[], ts)`
- `eval_runs(kind, engine, lang, slice, metric, value real, n int, details jsonb)`
- `audit_log(actor uuid, action, target, ts)`

RLS:
- Public (anon): `select` on approved `providers` and their `provider_services`, `provider_areas`, `working_hours`, plus `categories`, `issues`. Nothing else. `bookings` readable by id only through a server route (not direct anon select).
- Provider: full CRUD on rows where `provider_id` ∈ providers they own; read their `calls`, `call_turns`, `bookings`, `safety_events`.
- Admin: all.
- Agent worker + API use the **service role key** (server only; never in `web/` client bundles).
- Helper SQL functions: `is_admin()`, `owns_provider(pid uuid)`.
- Trigger: on `auth.users` insert → create `profiles` row with role from signup metadata (`provider` default; admin set manually).

## 8. Call flow (web)
1. Client `POST /api/calls/web {mode, provider_id?, test?}` → server creates `calls` row, room name `call_<uuid>`, returns `{token, url, roomName, callId}`; token grants join + includes room configuration dispatching agent `awazbot` with metadata JSON `{mode, provider_id, channel:"web", call_id, test}`.
2. Client navigates to `/call/[roomId]`, connects with `livekit-client` / `@livekit/components-react`, enables mic.
3. Agent worker entrypoint parses metadata, loads config, starts `AgentSession`, greets.
4. Transcripts shown via LiveKit transcription events; booking card via data topic `awaz.booking`; emergency via `awaz.events`.
5. On disconnect agent writes `ended_at`, `duration_s`, `outcome`, average latency.

## 9. WhatsApp
- Webhook `GET/POST /webhooks/whatsapp` (FastAPI), verify `X-Hub-Signature-256` with app secret, return 200 immediately, dedupe by message id, process in background.
- Routing: first message text containing a provider code (`[A-Z]+-\d{2}`) binds the conversation to that provider; otherwise directory mode.
- Voice notes: download media → ffmpeg to 16 kHz mono WAV → batch STT (Scribe) → same `awaz_core` brain in text mode (same instructions + tools, run with the LLM directly) → Azure TTS → ffmpeg to OGG/Opus → upload media → send audio + short text.
- Provider alerts: interactive message with Approve/Reject buttons (`button_reply.id = approve:<booking_id>` / `reject:<booking_id>`).
- Live calls: code path using the LiveKit WhatsApp connector, gated by `WHATSAPP_CALLING_ENABLED`. When false, the code must not run.

## 9b. Email notifications (Gmail)

- Module `core/awaz_core/notify_email.py` with `send_booking_email(booking, provider)`, `send_emergency_email(call, provider, rule)`, `send_test_email(to)`. Uses env `GMAIL_SMTP_USER`, `GMAIL_APP_PASSWORD`, `EMAIL_FROM_NAME`, `APP_PUBLIC_URL`. Timeout 10 s. Runs in a background task/thread so it never delays the voice conversation.
- Emails are **multipart: plain text + simple HTML** (inline CSS, no images), bilingual: English first, Urdu section below (RTL `dir="rtl"`). Subject formats:
  - `New booking: <issue> – <area> – <date time> [URGENT]`
  - `[EMERGENCY] <rule> reported by a caller – call back now`
- Body fields: business name, customer name, masked phone (full phone only inside the portal), problem as the customer said it, issue code + urgency, area/landmark, slot, channel (web / WhatsApp), booking status, button-styled link to `APP_PUBLIC_URL/provider/bookings?highlight=<id>`; P1 approve/reject signed links.
- Every attempt writes a `notifications` row. If `email_notifications=false`, skip email but still log `skipped` in the server logs.
- The web app's "Send test email" button calls `POST /api/notify/test-email` on the FastAPI service (server-side fetch from a Next.js server action with a shared `INTERNAL_API_SECRET` header), so SMTP credentials live only in the Python services.
- Gmail limits: a normal Gmail account can send a few hundred emails per day — fine for the MVP. Mention switching to a transactional provider later.

## 10. Evaluation
`eval/run_stt.py` (WER/CER via `jiwer` per engine × language × speaker group), `eval/run_classifier.py` (accuracy, confusion matrix, emergency recall on `scenarios.csv`), `eval/run_latency.py` (reads `call_turns.latency_ms`), all write to `eval_runs`. `scripts/check_health.py` pings every external service.

## 11. Non-functional
- Secrets only in `.env` files (git-ignored). Never log secrets. Never expose service role key, LiveKit secret, Gmail app password or `INTERNAL_API_SECRET` to the browser.
- Mask phone numbers in UI (`0300-***-4567`).
- No audio recordings stored in MVP (transcripts only); voice-note raw audio deleted after processing.
- Every external call has a timeout and a fallback (LLM timeout → templated reply for the current step).
- `DEMO_MODE=true`: seed data present, fixed demo provider "Khan Electric" (`KHAN-01`, Hayatabad).
- README contains a **model & dataset disclosure table** (name, provider, licence, purpose).

## 12. Out of scope (never build)
Payments, maps/geolocation, PSTN phone numbers, customer accounts/ratings, push notifications, native mobile apps, audio recording storage, multi-currency, analytics beyond the listed counts.
